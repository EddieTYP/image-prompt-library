# v0.7.10 OAuth Reliability Hotfix Design

## Goal

Close two post-release OAuth recovery gaps without changing the public API or broadening the generation feature set:

1. Treat an OAuth token-endpoint HTTP `408 Request Timeout` as a temporary provider failure.
2. Treat failures opening the private refresh lock file as temporary, redacted failures.

The intended release is `v0.7.10`, a stable patch release after `v0.7.9`.

## Context

`CodexNativeAuthStore.refresh_tokens()` already maps transport exceptions and upstream `5xx` responses to `CodexNativeTemporaryError`. HTTP `408` currently falls through to `CodexNativeAuthError`, which makes status handling look like a broken login.

`CodexNativeAuthStore._refresh_lock()` opens a private file next to the app-owned auth file. An `OSError` raised by that open can currently escape as raw text. Generation-job failure recording can retain that text, which may include the local auth/lock path.

## Design

### Token endpoint response classification

Map HTTP `408` and every `5xx` token-endpoint response to the existing `CodexNativeTemporaryError` with the existing neutral message:

`Token refresh is temporarily unavailable`

Keep all other non-`200` response handling unchanged. In particular, HTTP `400`, `401`, and `403` remain `CodexNativeAuthError` and continue to produce the existing re-login guidance.

### Refresh-lock open failure handling

Wrap only the lock-file open operation in `CodexNativeTemporaryError`. The public message must be the same neutral temporary message used for other refresh interruptions; it must not include the auth path, lock path, operating-system error text, or credentials.

Once the lock is open, retain the current advisory-lock behavior unchanged:

- persistent regular lock file;
- Windows `msvcrt` / POSIX `fcntl` advisory locking;
- 100ms polling, with a maximum 20-second wait;
- final token reread after a temporary wait failure;
- no stale-file cleanup protocol.

### Error propagation and UX

The existing `read_tokens()` temporary-error path must preserve a saved session as connected-but-unavailable in provider status. A generation job that encounters either hotfix case must receive the neutral temporary message and be classified as `provider_unavailable`; its error and metadata must not expose a local path or suggest re-login.

No endpoint shape, frontend component, OAuth credential format, lock-file name, or retry policy changes. The existing `auth_store_path` diagnostic field remains unchanged for API compatibility; the hotfix prevents paths from entering new temporary messages and generation-job error/metadata fields.

## Regression Coverage

Add focused tests that prove:

1. HTTP `408` refresh responses raise `CodexNativeTemporaryError`, preserve the saved credential file, and use the neutral message.
2. A simulated `OSError` while opening the refresh lock raises `CodexNativeTemporaryError` with the neutral message and does not include the local lock/auth path.
3. The generation-job path records the lock-open failure as `provider_unavailable` with no leaked path text.
4. Existing `400`, `401`, and `403` tests remain auth errors.

Run the OAuth-native focused suite, the generation-job regression coverage, and the production frontend build. GitHub Ubuntu CI remains the full-suite gate.

## Release Scope

After the patch is merged and CI is green:

- create GitHub Release `v0.7.10` with `isPrerelease: false`;
- describe it as an OAuth reliability hotfix;
- do not replace, retag, or alter the published `v0.7.9` stable release.

## Out of Scope

- General retry/backoff changes.
- New provider controls or UI copy.
- Filesystem-permission repair.
- Broader provider status redesign.
- Public-doc stable-release synchronization.
